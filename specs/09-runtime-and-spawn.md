## 运行时

应用用 `bun` 或 `node` 跑,各有最低版本(`MIN_BUN` / `MIN_NODE`)。版本探测是一次子进程调用,因此**在控制侧执行**:等待版本号是一个等待,而监督 tick 没有 await 点。不达标的项目在到达登记之前就被拒绝。

## spawn 契约

**独立会话。** 子进程 `setsid`,拿到自己的进程组。应用被自己的终端信号影响、以及我们按组发信号,都依赖这一条。

**只带自己的 stdio。** 守护进程持有的任何 fd(pidfd、socket、tty)要么 `CLOEXEC`,要么在 execve 前统一关闭。实测过应用会继承守护进程的 `/dev/ptmx`,这类继承既泄露也危险。

**环境是算出来的,不是继承的。** 白名单 + 项目的 `[env]` + 保留变量(`BM2_*`、`NODE_ENV`),顺序固定,`[env]` 覆盖应用自带 env 文件里的同名项,但永远覆盖不了保留变量。

**pidfd 钉住。** spawn 成功后立刻开 pidfd;失败(内核 < 5.3 或 fd 耗尽)按**启动失败**处理——管不了的进程不能留着。此时子进程已经被杀,善后见下。

## 崩溃判定与预算

- 干净退出且存活超过 `min_uptime_ms` → 重置连续异常计数(计数器本身就是判据,不需要额外标记)
- 连续异常达到 `max_restarts` → errored,不再重启
- 风暴窗口:短时间内的重启次数单独统计,用于通知阈值
- spawn 失败也计入预算,并按次数递增退避——瞬时失败重试,反复失败最终 errored

## 失败 spawn 的善后

两件事,都不在 tick 里等:

**杀。** 「组 + pid」两发:子进程是 fork 之后才 `setsid`,spawn 刚返回时它的进程组还不存在,只发组信号会漏掉,而 pid 从 fork 那刻起就有效。

**收。** 被杀的 pid 交给 tick 回收,窗口 500 ms 摊到多轮,每轮一次非阻塞尝试。列表有界(64),溢出丢最旧——一个僵尸只占一个 pid 表项,而卡住的 tick 会拖住一切。
