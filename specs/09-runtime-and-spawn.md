## 运行时

应用用 `bun` 或 `node` 跑,各有最低版本(`MIN_BUN` / `MIN_NODE`)。版本探测是一次子进程调用,所以**在控制侧执行**:等待版本号是一个等待,而监督 tick 没有 await 点。

不达标的项目在到达登记之前就被拒绝——错误发生在用户敲下 `start` 的那一刻,而不是等实例反复崩溃之后才发现。

## spawn 契约

**独立会话。** 子进程 `setsid`,拿到自己的进程组。应用不受启动它的终端影响、我们按组发信号,都靠这一条。

**只带自己的 stdio。** 守护进程持有的任何 fd(pidfd、socket、tty)要么 `CLOEXEC`,要么在 execve 前统一关闭。实测过应用会继承守护进程的 `/dev/ptmx`——这类继承既泄露也危险。

**pidfd 钉住。** spawn 成功后立刻开 pidfd。失败(内核 < 5.3 或 fd 耗尽)按**启动失败**处理:管不了的进程不能留着,此时子进程已经被杀,善后见下。

## 环境注入顺序

从低到高,后者覆盖前者:

1. 项目自带的 env 文件(如果 `exec_mode` 与运行时支持)
2. 白名单变量的当前值
3. 项目的 `[env]` 表
4. 保留变量(`BM2_*`、`NODE_ENV`、`PATH`)——**永远覆盖不了**

顺序是固定的,不随配置书写顺序变化。保留变量排最后,因为实例的自我描述不能由配置文件改写。

## 崩溃判定与预算

| 概念 | 判据 |
| --- | --- |
| 干净退出 | 存活超过 `min_uptime_ms`;此时重置**连续**异常计数 |
| 异常重启 | 未满 `min_uptime_ms` 就退出,或在期限内被判定为崩溃 |
| 达到预算 | 连续异常次数达到 `max_restarts` → errored,不再重启 |
| 风暴 | 窗口内的重启次数,单独统计,供通知阈值使用 |
| spawn 失败 | 同样计入预算,并按次数递增退避——瞬时失败重试,反复失败最终 errored |

「连续」是关键:计数器本身就是判据,不需要额外的标记位。

## 失败 spawn 的善后

两件事,都不在 tick 里等:

**杀,发两次信号。** 先发进程组、再发 pid。子进程是 fork 之后才 `setsid` 的,spawn 刚返回时它的进程组还不存在,只发组信号会漏掉,而 pid 从 fork 那刻起就有效。顺序不能颠倒。

**收,交给 tick。** 被杀的 pid 进回收列表,窗口 500 ms 摊到多轮,每轮一次非阻塞尝试。列表有界(64),溢出丢最旧——一个僵尸只占一个 pid 表项,而卡住的 tick 会拖住一切。

## 边界情形

| 情形 | 表现 |
| --- | --- |
| 内核无 pidfd(或 fd 耗尽) | 判定启动失败,杀子进程,计入预算 |
| 运行时版本不足 | `start` 阶段拒绝,项目不登记 |
| `script` 不存在 | 实例启动失败,计入预算;错误进 crash 日志 |
| `cwd` 不存在 | 同上 |
| 子进程 spawn 后立即退出 | 按异常重启处理(未满 `min_uptime_ms`) |
| 应用自己 fork 了孙子进程 | 按进程组处理,组信号会带上它 |
