# 04 · CLI ↔ 守护进程线协议

- 状态: active
- 覆盖测试: 见文末「条目 → 测试」表
- 与代码对账: 2026-10-13

## 传输

loopback TCP,加一个共享令牌。端点文件 `<state_dir>/daemon.endpoint`:第一行端口、第二行令牌,原子替换,权限 0600。

客户端**读一次、用同一个端点代次的两半**。分两次读会拿到这一代端口加下一代令牌,那个组合谁也认不出来——失败信息会指向「令牌错误」,而真正的原因是换班。

**令牌错即断连**,不回任何内容、不解释原因:给探测者区分「端口开着但令牌错」和「端口没开」的信息量,本身就是泄露。

帧是**长度前缀的 JSON**,编解码集中在 `src/protocol`。命令带应用名时 app 字段是**名字**,不是路径——客户端不传状态目录,守护进程自己知道,这是它的事。

## Request

| 字段 | 类型 | 谁用 | 缺省语义 |
| --- | --- | --- | --- |
| `protocol` | `Int32?` | 全部 | 缺失 = 早期对端,按失配处理 |
| `command` | `String` | 全部 | 必填 |
| `app` | `String?` | stop / remove / list / notify | 缺失 = 不限应用 |
| `config_path` | `String?` | start | 缺失 = 用客户端 cwd 下的 `bm2.toml` |
| `notify_target` | `String?` | notify | 缺失 = 全部目标 |
| `force` | `Bool?` | remove | 缺失 = false(优雅停止) |

`protocol` 是可选字段,这样早于版本化的对端仍能**解码**,失配按名字报出来,而不是变成一个无法解释的解码失败。

## Response

带 `protocol`、`ok` 与结果负载。`list` 的负载含实例数组与守护进程信息(守护进程只发一行,客户端决定要不要打印它)。

协议问题单独判:`protocol_problem` 一旦有值,CLI **先报它,不再解释后续内容**——版本不对时后面的字段没有可信的语义。

## 升版规则

`PROTOCOL_VERSION` 当前为 4。只有这两种情况必须升:

1. 对端**读不懂**——新增字段或新动词会让老守护进程拒绝请求
2. **含义变了**——字段仍能解析,但老端的处理与新端不同。例如 `force` 被老端静默忽略:要求强杀的一方得到优雅停止,还以为成功了

第二种比第一种危险,因为它不报错。版本不匹配时 CLI 给出可操作的一句话:提示运行 `bm2 reload`。

## 队列与超时

| 环节 | 容量 / 上限 | 理由 |
| --- | --- | --- |
| 命令队列 | 64 | 一条命令占一个 tick,调用方同时只有一条在飞 |
| 应答队列 | 1 | 调用方放弃等待只丢应答,不影响守护进程 |
| 等应答 | 15 s | 一般命令的耐心 |
| 等应答(重启类) | 按 `stop_timeout` 计算 | 一次完整重启要等得起 |
| 并发连接子任务 | 64(信号量) | 见 e2e 段 AE |

## 失败行为

| 情形 | 表现 |
| --- | --- |
| 守护进程不在 | CLI 报「未运行」,不是连接超时 |
| 令牌错 | 直接断连,无内容 |
| 版本失配 | 报协议问题 + 提示 `bm2 reload` |
| 未知动词 | `ok = false`,理由是未知命令 |
| 应用不在册 | `ok = false`,理由点名应用 |
| 等应答超时 | CLI 退出 1;守护进程侧不受影响(应答丢弃) |
