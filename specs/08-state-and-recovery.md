# 08 · 状态文件与恢复

- 状态: active
- 覆盖测试: 见文末「条目 → 测试」表
- 与代码对账: 2026-10-13

## 原子写

状态文件一律原子写:`<path>.tmp` + fsync + rename。断电时读到的是旧版本或新版本,不会是半份。

例外是**每个实例的状态文件**:它每次 spawn 都重写,内容可以由仍在运行的进程重建,所以用省掉目录 fsync 的快速原子写。一个项目实例多时,省下的是每次启动、每个实例一次 fsync。

## 文件

| 路径 | 内容 | 谁写 |
| --- | --- | --- |
| `<name>/project.json` | `{ config_path, stopped }` | 控制面(登记 / 停止 / 注销) |
| `<name>/<name>-<id>.json` | 一个实例的监督状态 | 监督任务(每次 spawn) |

实例状态记录:pid、pidfd、状态、启动墙钟与单调钟、各期限(内存检查、reuseport 探测)、启动次数、连续异常重启次数、退出意图、最后一次退出码或信号。

**它的用途只有一个**:守护进程重启后收养仍在运行的实例。它不记录日志、不记录环境变量值、不记录配置内容。

## 恢复流程

1. 校验状态目录归属(它持有控制面令牌)
2. 扫 `<state_dir>` 下的一级目录,读各自的 `project.json`
3. 按 `config_path` 加载配置
4. **登记项目,不自动启动停止中的项目**——`stopped` 为真时只登记,等 `start`
5. 实例:仍是自己的子进程就用 pidfd 收养,已经消失的走正常重启路径

第 2 步只看一级目录:嵌套目录不是项目,状态目录顶层那三份守护进程日志也不属于任何项目。

## 边界情形

| 情形 | 表现 |
| --- | --- |
| `project.json` 存在但配置读不出来 | 记 `project_load_failed`,跳过该项目,不启动 |
| `project.json` 不存在 | 该项目不算在册——`clean` 的判据正是这一条 |
| 实例状态文件解析失败 | 视为没有该实例,不动进程(进程可能已经不在,也可能还在跑) |
| 实例状态文件存在但进程已消失 | 按正常重启路径处理,尊重 `max_restarts` |
| 状态目录不存在 | 首次运行,创建 |

## 兼容性

项目还没有外部使用者。格式变更直接改,**不写迁移代码**;改变字段含义要连带更新本文与 `02-project-identity.md` 里那句字段说明。
