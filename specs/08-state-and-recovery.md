# 08 · 状态文件与恢复

- 状态: active
- 覆盖测试: `src/core/recovery_wbtest.mbt`、`src/core/supervisor_wbtest.mbt`
- 与代码对账: 2026-10-13

## 原子写

状态文件一律原子写:`<path>.tmp` + fsync + rename。关掉电源时读到的是旧版本或新版本,不会是半份。

例外是每个实例的状态文件(`<name>-<id>.json`):它每次 spawn 都会重写,内容可以由运行中的进程重建,所以用去掉目录 fsync 的快速原子写——一个项目实例多时,省下的是每次启动每个实例一次 fsync。

## 文件

```
<name>/project.json     登记记录:{ config_path, stopped }
<name>/<name>-<id>.json 一个实例的监督状态
```

实例状态记录 pid、pidfd、状态、三个时钟(启动墙钟、启动单调钟、各期限)、启动次数、连续异常重启次数、退出意图与最后一次退出码/信号。它的用途只有一个:**守护进程重启后收养仍在运行的实例**。

`project.json` 是「这个名字登记着」的唯一凭证。它存在但配置读不出来时,项目记一条 `project_load_failed` 并跳过,不会被启动。

## 恢复流程

1. 校验状态目录归属(它持有控制面令牌)
2. 扫 `<state_dir>` 下的一级目录,读各自的 `project.json`
3. 按 `config_path` 加载配置;加载失败记事件并跳过
4. 登记项目。**不自动启动停止中的项目**——`stopped` 为真时只登记
5. 实例:仍是自己的子进程就用 pidfd 收养;已经消失的按正常重启路径处理

## 与「无主目录」的关系

`bm2 clean` 的判据正是这里:`project.json` 不存在即为无主。这个判据是**保守**的——登记一定先写这份文件,所以最坏情况只是把已注销的误当成还在而跳过,不可能删掉在册项目的日志。见 `03`。

## 兼容性

项目还没有外部使用者。状态文件格式变更时直接改,不写迁移代码;改变字段含义要连带调整 `02` 里那句「`project.json` 的字段」。
