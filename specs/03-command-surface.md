## 词汇表

| 命令 | 行为 |
| --- | --- |
| `start` | 读当前目录 bm2.toml,登记并启动;对已停止的项目即恢复 |
| `stop <app>` | 优雅停止,**留在册**,守护进程重启后不复活 |
| `remove <app>` | 优雅停止 → 交还名字 → 清登记与状态,**日志保留** |
| `remove <app> -f/--force` | 硬杀 → 交还名字 → 连状态目录一起清(含日志) |
| `clean [--dry-run]` | 扫掉无主的历史目录,默认列出并删除 |
| `kill [-y]` | 无参:杀所有应用并退出守护进程 |
| `list [app] [--json]` | 状态;未过滤时带一行守护进程信息 |
| `check` | 校验当前目录的 bm2.toml |
| `reload` | 换一个新二进制,应用不动 |
| `notify [target]` | 往通知目标发一条测试消息 |
| `upgrade` | 自升级 |
| `version` | 版本 |

## 层次原则(硬规矩)

**`kill` 只管守护进程。** 它带应用名一律报错并指路到 `stop` / `remove`——同一个动词横跨两个层次,读的人就得记住两套语义,帮助文本自己也解释不清。

应用的生命周期由 `stop`(停)与 `remove`(退役)表达,`clean` 收拾它们留下的无主残留。不允许再出现「某个动词顺手管一下应用」的写法。

## 两个语义细节

**`stop` 必须持久。** 「停止但留在册」意味着守护进程重启或换二进制之后**不能**把它自动拉起。停止标记写进 `project.json`,恢复时尊重它;只有 `start` 清除。

**`remove -f` 的目录清理在客户端做。** 守护进程只负责注销(它已经删掉 `project.json` 与实例状态文件),CLI 等 `list` 里该项目消失之后再删 `<state_dir>/<name>/`。这样顺序天然正确:停 → 收 → 删。守护进程没在等待窗口内收尾就报错退出,不假装成功。

## 退出码

- `0` 成功
- `1` 失败(守护进程拒绝、连接不上、目标不存在)
- `2` 用法错误(argparse 拦下,例如 `-y` 与应用名同用)

## 一个 bm2.toml = 一个项目

`start` 只登记当前目录那一个项目。两个目录同名的处理见 `02`——后者被拒,不会并进前者。
