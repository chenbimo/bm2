## 命令逐条

### `start`

在项目目录执行。读 `bm2.toml` → 校验 → 登记并启动。对**已停止**的项目即恢复运行(清除停止标记)。

- 配置非法:退出 1,报具体字段
- 同名但配置文件不同(**规范化路径**后比较):退出 1,报占用者路径与两条出路(改名,或先 `remove`)
- 同名同文件:放行,刷新配置——这是应用配置变更的正常路径
- 重复调用:幂等,等价于一次完整重启

### `stop <app>`

优雅停止(SIGTERM,超 `stop_timeout_ms` 后 SIGKILL),**留在册**。

- 已经在册但已停止:幂等,不报错
- 名字不在册:退出 1
- **必须持久**:停止标记写入 `project.json`,守护进程重启或换二进制之后不得自动拉起;只有 `start` 清除它

### `remove <app>` / `remove <app> -f`

优雅退役:停实例 → 注销 → 删 `project.json` 与实例状态文件。**日志保留**。

`-f` 另外清掉整个 `<state_dir>/<app>/`,而且**这一步由 CLI 执行**:守护进程只负责注销,CLI 等 `list` 里该项目消失之后再删目录。顺序是停 → 收 → 删,不能颠倒——应用还握着 fd 时删目录,空间要等进程真正退出才释放。

- 名字不在册:退出 1,不静默通过(敲错名字看起来像成功是最坏的结果)
- `-f` 在等待窗口内没等到守护进程收尾:退出 1 并说明文件已保留,不假装成功
- 注销后同名可以重新登记,新项目不继承上一代的统计、风暴历史与探测标记

### `clean [--dry-run]`

扫 `<state_dir>` 下的一级目录,**没有 `project.json` 的即为无主**。默认逐条列出并删除;`--dry-run` 只列不动。

- 纯本地,不需要守护进程(迁移、换机器之后正是这种场景)
- **只碰无主目录**:判据保守——登记一定先写 `project.json`,所以最坏只是漏删,不可能删掉在册项目的日志
- 不碰状态目录顶层守护进程自己的三份日志
- 目录里若有 bm2 没写过的文件,留在原地并在 stderr 说明原因

### `kill [-y]`

杀所有应用(硬杀 + 注销)然后退出守护进程。**带应用名一律报错**,指路到 `stop` 或 `remove`;`-y` 与应用名同用也是用法错误(退出 2)。

## 层次原则(硬规矩)

`kill` 只管守护进程。应用的生命周期由 `stop`(停)与 `remove`(退役)表达,`clean` 收拾它们留下的无主残留。不允许再出现「某个动词顺手管一下应用」的写法——同一个动词横跨两个层次,读的人就得记两套语义,帮助文本自己也解释不清。

## 退出码

| 码 | 含义 |
| --- | --- |
| 0 | 成功 |
| 1 | 失败:守护进程拒绝、连不上、目标不存在 |
| 2 | 用法错误(argparse 拦下,不询问守护进程) |
