## 清单与产物

发布站提供一份 JSON 清单。形态:

```json
{
  "version": "0.3.0",
  "artifacts": [
    { "name": "bm2",  "target": "x86_64-linux", "url": "...", "sha256": "...", "fileSize": 1234567 },
    { "name": "bm2d", "target": "x86_64-linux", "url": "...", "sha256": "...", "fileSize": 2345678 }
  ]
}
```

`target` 由二进制**自己的 ELF 头**判断(`e_machine` 为 0xB7 即 aarch64,其余按 x86-64)——不调子进程、不猜平台。

## 流程

1. **端口预检** — 目标端口能不能用,先确认再动手
2. 取清单(超时 30 s),按版本号判断是否有新版
3. 下载本平台的两个二进制(超时 300 s)并逐一校验 SHA256
4. **事务性换入**:先备份为 `.bak`,任一步失败走 restore 回滚;全部成功才删备份
5. **换班**:先让旧守护进程 `request_detach`(放掉控制面文件后退出,**应用不动**),再交换二进制
6. 新守护进程启动并收养仍在运行的实例

第 5 步这个顺序是补出来的:原实现直接交换二进制,没人通知旧守护进程退出——「无缝应用」从来没有真正生效过。新加的 e2e 段立刻抓到了它。

## 失败分支

| 情形 | 表现 |
| --- | --- |
| 端口被占 | 预检即退出 1,不下载任何东西 |
| 清单取不到 / 解析失败 | 退出 1,现有二进制未动 |
| SHA256 不匹配 | 退出 1,回滚,不留半份产物 |
| 下载中断 | 同上 |
| 备份失败 | 退出 1,不动现有二进制 |
| 交换中途失败 | restore 回滚到 `.bak` |
| 新版起不来 | 回滚;应用仍在旧守护进程**退出前**的进程组里,重新 `start` 即可收养 |

## 脚本侧的产物解析

构建脚本一律**按名字**解析产物,并断言它新于自己包内的最新源文件。moon 在版本之间搬过 native 产物的目录,硬编码路径会匹配到搬移前的旧副本——e2e 于是跑着旧二进制照样绿灯。这个坑踩过一次,规则写进 `AGENTS.md`。

## 清单签名:明确不做

现状是 HTTPS + 同源 SHA256 完整性校验 + `.bak` 事务回滚。没有签名意味着:发布站被攻破时,清单与产物可以被一起换成自洽的一整套。

不做的理由,记在这里免得反复讨论:

- 生态里没有成熟的 Ed25519 实现(唯一候选是个人的、依赖另一个个人包、数月未更新),按依赖规则不可用
- RSA 有合规的社区包(`proton_rsa`,只做验证),但为一个窄场景引入新依赖,收益不划算
- `x/crypto` 只有哈希、AES、chacha 与 HMAC,没有非对称签名——自己实现签名算法正是本项目一直避免的事

**若将来要做,方案已定**:签清单的**原始字节**(先验签再解析,发布侧怎么排版 JSON 都不影响),公钥内置为常量,验签失败拒绝升级并记事件(fail closed)。
