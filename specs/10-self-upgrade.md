# 10 · 自升级

- 状态: active
- 覆盖测试: `src/cmd/bm2/upgrade_wbtest.mbt`、e2e 段 AD / AF
- 与代码对账: 2026-10-13

## 清单与产物

发布站提供一份 JSON 清单:版本号加一组产物,每个产物带 `name`、`target`、`url`、`sha256`、`fileSize`。`target` 由二进制**自己的 ELF 头**判断(`e_machine` 为 0xB7 即 aarch64,其余按 x86-64),不调子进程、不猜平台。

## 流程

1. **端口预检** — 目标端口能不能用,先确认再动手
2. 取清单(30 s 上限),按版本号判断是否有新版
3. 下载本平台的两个二进制(300 s 上限)并逐一校验 SHA256
4. **事务性换入**:先备份为 `.bak`,任一步失败走 `restore` 回滚;全部成功才删备份
5. **换班**:先让旧守护进程 `request_detach`(它放掉控制面文件后退出,应用不动),再交换二进制
6. 新守护进程启动并收养仍在运行的实例

第 6 步这个顺序是补出来的:原实现直接交换二进制,没人通知旧守护进程退出——「无缝应用」从来没有真正生效过。新的 e2e 段立刻抓到了它。

## 脚本侧的产物解析

构建脚本一律**按名字**解析产物,并断言它新于自己包内的最新源文件。moon 在版本之间搬过 native 产物的目录,硬编码路径会匹配到搬移前的旧副本——e2e 于是跑着旧二进制照样绿灯。这个坑踩过一次,规则写进 `AGENTS.md`。

## 清单签名:明确不做

现状是 HTTPS + 同源 SHA256 完整性校验 + `.bak` 事务回滚。没有签名,意味着发布站被攻破时,清单与产物可以被一起换成自洽的一整套。

不做的理由,记录下来免得反复讨论:

- 生态里没有成熟的 Ed25519 实现(唯一候选是个人的、依赖另一个个人包、且已数月未更新),按依赖规则不可用
- RSA 有合规的社区包(`proton_rsa`,只做验证),但为一个窄场景引入新依赖,收益不划算
- `x/crypto` 只有哈希、AES、chacha 与 HMAC,没有非对称签名——自己实现签名算法正是本项目一直避免的事

**若将来要做,方案已定**:签的是清单的**原始字节**(先验签再解析,发布侧怎么排版 JSON 都不影响),公钥内置为常量,验签失败拒绝升级并记事件(fail closed),测试用密钥对覆盖「通过 / 篡改一字节被拒 / 缺签名字段被拒」三种情形。
