# 07 · 通知与上报

- 状态: active
- 覆盖测试: 见文末「条目 → 测试」表
- 与代码对账: 2026-10-13

## 分工

事件 → 多语言消息 → 报告 → 投递。监督侧只**发布**(投进队列);网络、去重、限流、重试全部由 notify 任务独占,不在 tick 里。

**投递失败只记事件,绝不改变监督行为。** 一个死掉的通知端点不能让任何应用重启或退出——这条比通知本身重要。

## 策略属于项目

`[notify]` 写在项目的 `bm2.toml` 里,随项目独立生效。项目注销时,它留在通知侧的状态(队列、限流窗口、去重记录)一并回收——见条目表最后一行。

| 字段 | 作用 |
| --- | --- |
| `enabled` | 总开关 |
| `lang` | 面向人读的文案语言(事件日志的键保持语言中立) |
| `dedupe_window_s` | 同一签名的去重窗口 |
| `max_per_minute` | 滚动限流;超限丢弃并按窗口记一条事件 |
| `queue_size` | 待投递队列上限(≤ 4096),满则丢最新 |
| `[[notify.report]]` | 报告条目:周期、事件过滤、内存与重启阈值 |
| `[[notify.report.target]]` | 目标:类型(webhook / SMTP)、地址、凭据 |

## 线上契约(不可协商)

**数值以字符串发送。** payload 里的数字保持字符串形式,与既有接收方逐字一致——浮点格式化会把 `42` 变成 `42.0`,而下游按字符串做匹配。

**凭据不进任何地方。** `url` / `secret` / `username` / `password` 不得进入事件、状态文件、日志或 CLI 输出。配置校验出错只报字段名与 `target[i]` 下标。

**投递理由不带服务器原文。** 失败原因可能被服务端回显请求内容,而请求里就是 base64 凭据。

**SMTP 必须 STARTTLS。** 中继拒绝 STARTTLS 就中止——宁可发不出去,也不在明文上传凭据。e2e 有一条断言专门盯这个:明文的中继**绝不能**看到 `AUTH PLAIN`。

**认证顺序:先 `AUTH PLAIN`,中继回 504(机制不支持)时回落 `AUTH LOGIN`。** 其余应答码按凭据被拒处理,不再尝试别的机制。

## 重试与丢弃

重试 3 次,退避递增;三次用尽记事件后丢弃。丢弃、被限流、被去重的消息**只留事件,不留正文**——排查要看的是「谁在什么时候丢了多少」,不是「丢的内容是什么」。
