# 07 · 通知与上报

- 状态: active
- 覆盖测试: `src/notify/notify_wbtest.mbt`、`src/core/alert_wbtest.mbt`、e2e 段 AG / AH / AI / AJ
- 与代码对账: 2026-10-13

## 分工

事件 → 多语言消息 → 报告 → 投递。监督侧只**发布**(投进队列),投递由 notify 任务独占:网络、去重、限流、重试都不在 tick 里。

投递失败只记事件,**绝不改变监督行为**。一个死掉的通知端点不能让任何应用重启或退出。

## 策略属于项目

`[notify]` 写在项目的 `bm2.toml` 里,随项目独立生效:收件人、目标、阈值、报告周期都是这个项目自己的事。项目注销时,它留在通知侧的状态(队列、限流窗口、去重记录)一并回收。

## 线上契约

- **数值以字符串发送**:payload 里的数字保持字符串形式,保证与既有接收方逐字一致(浮点格式化会把 `42` 变成 `42.0`)
- **凭据不进任何地方**:`url`/`secret`/`username`/`password` 不得进入事件、状态、日志或 CLI 输出;校验错误只报字段名与 `target[i]` 下标
- **投递理由不带服务器原文**:失败原因可能被服务端回显命令,而命令里就是 base64 凭据
- **SMTP 必须 STARTTLS**:中继拒绝 STARTTLS 就中止,宁可发不出去也不在明文上传凭据。e2e 有一条断言专门盯着:明文的中继**绝不能**看到 `AUTH PLAIN`
- **认证**:`AUTH PLAIN` 优先,中继回 504(不支持的机制)时回落 `AUTH LOGIN`;其余应答码按凭据被拒处理

## 限流与重试

- 去重窗口 `dedupe_window_s`:同一签名在此窗口内只投一次
- 滚动限流 `max_per_minute`:超限丢弃,按窗口记一条事件,不逐条刷屏
- 队列上限 `queue_size`(≤ 4096):满则丢最新
- 重试 3 次,退避递增;三次用尽记事件后丢弃

## 一个刻意的取舍

被丢弃、被限流、被重试耗尽的消息只留事件,不留正文。事件日志与状态文件都保持语言中立、不含敏感内容——排查要看的是「谁在什么时候丢了多少」,不是「丢的内容是什么」。
